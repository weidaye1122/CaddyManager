# 本地空间与清理计划

## 范围和原则

适用于 `CaddyManager/` 和旁边的 `本地资料/`。本计划是维护规则，不是已经启用的定时任务；没有自动删除操作，不涉及服务器、系统缓存或其他项目。

先看实际占用和文件用途，再选择清理对象。时间和大小仅用于提醒检查，不能单独决定删除。优先处理可重新生成的产物和重复材料，保留唯一数据、未完成工作的证据及恢复所需文件。

## 检查频率

| 时机 | 做什么 |
| --- | --- |
| 每次开发或验证结束 | 关闭本次启动的测试进程；清理由本次任务创建、已完成用途的临时副本和测试账号数据；保存必要结果和复现方法 |
| 每次正式发版后 | 确认远端附件完整且可以下载，整理本地重复构建包，关联版本与验证记录 |
| 持续开发期间每月一次 | 查看目录占用，检查旧日志、截图、构建包和备份是否仍有用途 |
| 连续两个月没有开发 | 检查是否值得移除可重建的开发环境；保留源码、依赖清单和数据 |
| 工作区超过 1 GiB，或截图与验证材料超过 200 MiB | 提前检查增长来源；达到阈值不会触发自动删除 |

不持续开发时不必为执行月度检查而启动服务，下次恢复工作时补查即可。

## 各类文件怎么处理

| 内容 | 保留与清理规则 |
| --- | --- |
| 源码、文档、`.git/` | 长期保留。历史版本由 Git 管理，不复制多个“最新版”目录；不手动删 Git 内部文件 |
| 未提交或未跟踪的工作 | 保留。清理前查看 `git status`，不能把“未跟踪”直接当作垃圾 |
| `legacy/` | 是纳入版本管理的历史代码；如需移除，按正常代码修改和回归流程处理，不按缓存清理 |
| `.venv/` | 活跃开发期间保留。连续两个月不用且需要腾空间时，可在确认 Python 和依赖来源可用后重建；没有空间压力时不必删除 |
| `__pycache__/`、`.pytest_cache/` | 可重新生成，相关进程停止后可清理。不要为清理少量缓存反复重建整个环境 |
| `dist/`、重复下载的源码包 | 正式附件已发布、下载及校验正常后，本地通常保留最新两个已验证版本即可；较旧重复包可列入清理。尚未发布的候选包、唯一恢复包和待排查失败包另行保留 |
| `.local/data/` | 是本地运行数据，不是缓存。需要保留的账号和测试场景继续保存；明确结束的一次性测试可在停服务后清理或归档 |
| 普通测试日志、过程截图 | 通常保留 30 天。任务完成后保留结论、关键截图和复现方法；到期的重复过程材料可列入清理 |
| 正式版本或问题排查证据 | 结论、环境、版本、复现方法和关键证据长期保留。大体积原始材料在对应问题关闭至少 90 天后再检查；仍有问题、用于恢复或被文档引用的材料继续保留或先更新引用 |
| 普通本地测试备份 | 按来源分别保留最近 3 份有效备份。超过 30 天的更早备份仅在存在可用替代副本时列入清理 |
| 升级前备份、真实数据备份 | 至少保留最近两个已验收版本对应的完整恢复集合。未验收升级的前一份备份、唯一副本和恢复依赖项不清理；归档到其他存储后先验证可读取和恢复范围 |
| 讨论记录、修改总结 | 体积通常很小，长期保留。合并重复记录时保留决定、依据和相关链接 |

这里的“最近 3 份”和“最近两个版本”都是按数据来源或环境分别计算，不能把不同来源的备份混在一起计数。需要保护的备份取并集；保留规则不是文件数上限。

## 每次实际清理的步骤

1. 查看占用、当前工作区状态和相关进程，明确本次清理范围。
2. 列出候选文件或目录、用途、预计释放空间及保留依据。跳过归属不明、仍在写入或只能找到一份的资料。
3. 需要归档的内容先核对归档结果，再处理原副本；同盘移动并不等于释放空间，也不构成独立备份。
4. 根据本次清理任务的授权执行。不要用按日期删除整个工作区、`git clean -fdx` 或跨项目的批量删除命令。
5. 对比前后占用，确认源码和保留材料完整、文档引用仍有效。涉及环境重建时运行统一检查；只删旧日志或截图不需要重跑应用测试。
6. 在 `本地资料/讨论与记录/` 简要记录清理日期、范围、释放空间及保留位置。一次清理留一份结果，不为每个文件生成重复记录。

在仓库目录中，可先用下面的只读命令检查：

```bash
git status --short
du -sh . ../本地资料
git count-objects -vH
```

如果占用主要来自 Git，先查明是否误提交了大文件；修复仓库历史应作为独立任务处理，不直接删除 `.git/` 或强制清空恢复记录。
