# 发布、备份与恢复

本文件描述当前脚本的工作方式和操作顺序，不代表任何服务器已安装或已完成验证。服务器操作前先核对 SSH 别名、实际服务、文件路径和数据归属。

## 区分开发与发布

- 本地修改、Git 提交、推送到远端、创建版本标签和部署到服务器是不同步骤，记录时分别说明。
- `VERSION` 保存版本号。发布时同步 README 的版本说明和 `CHANGELOG.md`，检查后创建对应 `vX.Y.Z` 标签。
- 日常改动先写进 CHANGELOG 的“未归入新版本”，发布时再归入版本和日期；文档整理不必单独提升版本。
- 根目录 `install.sh` 默认下载最新正式 Release 的附件，使用 `CADDY_MANAGER_VERSION=vX.Y.Z` 固定正式版本；没有正式版本、缺包或校验失败即明确报错停止，不回退开发代码。日常推送不改变默认安装版本。
- 在本地源码目录执行根目录入口也会下载正式包。安装当前源码应明确执行 `scripts/install.sh`，两条路径不再混用。
- 安装脚本将程序及 `VERSION` 复制到 `/opt/caddy-manager/`，并保存 `install-info.json`，记录版本、标签、提交、来源和安装状态。源码目录安装不会被标记为正式 Release。
- `ready` 仅代表脚本的服务检查完成；异常退出会尽量记录 `failed`，被强制终止时可能停留在 `installing`，两者均需核查。旧安装没有记录时不推断其版本。
- 完整发版步骤及实际发布附件的安装、升级、回滚验收见 [正式发版流程](RELEASING.md)。

## 服务器升级前后

发布 Release 与服务器升级分开执行。下面步骤仅用于已授权的服务器操作；只做本地维护或发版时不连接服务器。

1. 记录本次范围、完成条件和实际验证结果，运行 `bash scripts/check.sh`。
2. 涉及 UI 时完成页面检查；涉及 Caddy、安装或服务时，在相应的隔离环境验证。固定开发依赖通过不代表发行版依赖已经通过。
3. 核对目标服务器和既有安装配置，记录旧版本、实际数据路径、服务状态及恢复方法。
4. 在暂停配置写入的维护窗口备份面板数据，并保存旧程序、服务配置和实际 Caddy 存储。核验备份可读取且范围完整。
5. 按授权部署确定的版本。核对登录、站点列表、代理可访问、HTTPS、服务状态，记录新版本和结果。
6. 检查失败时停止继续变更，按备份的程序、配置和数据配套恢复，保留失败现场的必要记录。

## 默认安装位置

下表是当前安装脚本的默认值，实际路径以目标机器配置为准。

| 内容 | 默认位置 |
| --- | --- |
| 面板程序 | `/opt/caddy-manager/` |
| 版本及安装状态 | `/opt/caddy-manager/VERSION`、`/opt/caddy-manager/install-info.json` |
| 管理员、站点、生成的 Caddyfile、配置备份 | `/var/lib/caddy-manager/` |
| 面板环境配置 | `/etc/caddy-manager.env` |
| 面板服务 | `/etc/systemd/system/caddy-manager.service` |
| Caddy 服务覆盖配置 | `/etc/systemd/system/caddy.service.d/caddy-manager.conf` |
| 安装前配置和备份脚本输出 | `/var/backups/caddy-manager/` |
| Caddy 证书及账户存储 | 由 Caddy 用户环境和存储配置决定，必须在目标机器核实 |

查看服务：

```bash
sudo systemctl status caddy-manager
sudo systemctl status caddy
```

## 三种备份的范围

| 方式 | 包含 | 不包含 |
| --- | --- | --- |
| 面板中的“导出” | 站点规则 JSON | 账号、程序、服务配置、证书 |
| `scripts/backup.sh` | 指定的面板数据目录和环境文件 | 程序、systemd 服务与覆盖配置、Caddy 自身证书和账户存储 |
| 安装脚本的自动备份 | 当时存在的 `/etc/caddy/Caddyfile`、面板环境文件、Caddy 覆盖配置、旧版本及安装记录 | 完整程序及运行数据，不等于升级前的完整备份 |

默认安装可使用：

```bash
sudo /opt/caddy-manager/scripts/backup.sh
```

备份脚本不会读取或解析环境文件。使用自定义路径时，明确传入实际值，例如：

```bash
sudo env CADDY_MANAGER_DATA=/实际数据目录 \
  CADDY_MANAGER_ENV_FILE=/实际环境文件 \
  CADDY_MANAGER_BACKUP_DIR=/实际备份目录 \
  /opt/caddy-manager/scripts/backup.sh
```

执行前保证期间没有面板配置写入；必要时停止面板服务，Caddy 可继续提供已有代理。完成后恢复面板服务。不要在运行中把多次不同状态的文件混成一份备份。

备份包含账号哈希和站点信息，使用受限目录保存。用 `tar -tzf` 检查归档文件列表，再解压到独立临时目录验证所需文件、JSON 格式和 Caddyfile，避免直接覆盖正在运行的目录。额外备份旧程序和 Caddy 实际存储后，才具备相应范围的整机恢复材料。

## 恢复步骤

### 仅恢复站点规则

先导出当前规则，再通过面板导入可信的站点 JSON。**导入会替换整个站点列表，并重新生成站点 ID，不是合并。** 在真实运行模式下它会校验和应用 Caddy 配置；管理员账号保持不变。验证列表、备注、启停及代理结果。

### 恢复面板数据和程序

1. 确认需要恢复的时间点、程序版本、备份内容和目标路径，先备份当前状态。
2. 将归档解压到临时目录，检查 `sites.json`、已有账号的 `auth.json`、Caddyfile、环境文件；尚未设置账号的备份可能没有 `auth.json`。
3. 停止面板写入。保留当前数据目录和配置后，再恢复选定备份；使用匹配的数据与程序版本，不能默认旧程序支持新数据格式。
4. 恢复或核对环境配置、面板服务和 Caddy 覆盖配置中的路径。程序损坏时从已保存的对应版本源码恢复。仅恢复数据归档不能恢复丢失的程序与服务文件。
5. 核对服务用户的访问权限。默认面板用户为 `caddy`，管理员文件权限为 `600`，面板环境文件为 `600`；不要一律放宽为全员可写。
6. 使用实际 Caddy 二进制校验恢复的 Caddyfile；成功后再按实际服务配置重载 Caddy、启动面板。修改 systemd 文件后需先执行 `systemctl daemon-reload`。
7. 验证原账号登录、完整站点列表、代理、HTTPS 和服务状态。结果正常后再结束维护，保留前一份备份。

Caddy 证书存储的恢复需要匹配它的实际存储位置和权限，独立安排。不要把站点 JSON 导入成功当作证书或整机恢复成功。

`scripts/uninstall.sh` 用于卸载面板并保留数据，不是通用的版本回滚工具；其行为不能替代上述恢复核对。

现有安装脚本没有程序升级失败后自动切回旧版本的能力。需要回滚时，使用升级前保存的旧程序、配套数据、环境及服务配置按上述步骤恢复；不能只重新安装旧版本就假定数据和证书已经恢复。正式发版需在一次性环境实际演练这一过程，并记录旧、新版本及结果。

## 恢复演练的记录

在隔离环境中创建测试账号与站点，备份，修改或清空测试副本，再从备份恢复。检查账号、站点、备注、启停、配置和文件权限；记录环境、版本、归档范围、执行步骤及结果。

本机开发模式可以验证数据持久化和导入导出。真实 Caddy、证书、systemd、发行版安装及整机恢复必须在相应环境演练后才能标记完成。
